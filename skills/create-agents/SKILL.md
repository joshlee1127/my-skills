# 工時估算表 → AGENTS.md

## 這個技能要解決的問題

工時估算表是專案的**範圍合約**：客戶付的是表上那幾條作業項目的錢，多做的沒收錢、少做的要被追。
把代理人放進這種專案時，最大的風險不是它做不好，而是它**熱心地做了表上沒有的事**——多裝一個工具、多掃一個網段、順手改一個設定。

所以這裡產出的 AGENTS.md，本質是一份**把估算表翻譯成代理人可執行邊界**的文件：
每一條作業項目要能回推到表上的項次，表上沒有的一律不寫進去。判斷「要不要加這句」時，
問題永遠是「這句話能指回估算表的哪一列？」——指不回去就不要寫。

## 流程

### 1. 解析估算表

```bash
python <skill>/scripts/read_estimate.py <估算表路徑> --format md   # 人看的大綱，直接讀
python <skill>/scripts/read_estimate.py <估算表路徑> --out out.json  # 要程式接續處理時用
```

在 Windows 上把輸出接管線給另一支程式容易踩到 cp950 解碼問題，需要接續處理就用 `--out` 寫檔。

腳本已處理標題列不在第一列、分類欄合併儲存格、區塊尾端「小計」列這幾個常見情況，
不要自己另寫解析程式。**先看輸出開頭的 ⚠️ warnings**：手工維護的估算表常有資料打錯欄
（真實案例：標題「驗收項目」在 K 欄、內容打在 L 欄），這些內容會收在 `extra` 裡等你判斷歸屬，
不要當成雜訊略過——那通常正是驗收標準。判斷不出該歸哪一節、或內容本身模稜兩可時，
別用猜的塞進某一節，照 `references/clarifying-questions.md` 的追問協議問一輪。

若來源是 csv 或格式古怪到腳本解不動，直接讀原始內容手工整理，但仍要保住「分類／項目／備註／驗收」四類資訊。

### 2. 判斷作業性質（決定 §10 怎麼寫）

看作業項目的動詞，這會決定整份 AGENTS.md 的安全基調：

| 動詞樣態 | 性質 | §10 安全性的寫法 |
|---|---|---|
| 檢視、盤點、檢查、分析、確認、製表 | 唯讀健檢／稽核 | 一切作業唯讀，絕不變更客戶正式環境 |
| 建置、安裝、部署、移轉、設定、升級 | 變更型導入 | 需變更視窗、回復計畫、變更前備份與核准 |
| 兩者都有 | 混合 | 明確切開哪些項次唯讀、哪些允許變更 |

判斷不確定時照 `references/clarifying-questions.md` 的追問協議問使用者，不要猜——
這條寫錯，代理人就會在客戶生產環境上做錯事。

### 3. 補齊表上沒有的資訊

估算表不會寫的、但 AGENTS.md 需要的，照 `references/clarifying-questions.md` 的追問協議問——
先查事實、只問真決策、當輪能問的一次列完，等使用者回答後才問下一輪解開的題目：

- 客戶／專案名稱與代理人角色定位（例：SRE、資料工程、應用開發）
- 交付文件與原始資料的存放位置約定（`doc/`、`data/`、是否進版控）
- 是否需要同步到外部平台（SharePoint、Notion…）及方向限制
- 已安裝／可用的技能清單（見步驟 4）

推得出來的不要問：專案名稱通常在檔名或表頭，據點與設備型號通常散在備註欄——這些用讀檔、
查估算表就有答案，不要包成問句丟給使用者。「是否同步到外部平台」與「同步方向限制」是
前後兩輪的題目，不要在還沒確定要不要同步前就先猜方向限制怎麼問。

### 4. 盤點可用技能，不要發明技能

先看實際裝了什麼，再做對應：

```bash
ls ~/.claude/skills/ .claude/skills/ .agents/skills/ 2>/dev/null
```

每個**項目分類**去找一個對應技能。對應原則與「找不到怎麼辦」見
`references/skill-mapping.md`——這份要讀，因為寫錯的代價是代理人去呼叫不存在的技能，
或反過來裝了一個帶破壞性操作的技能來做唯讀健檢。

**只有這份清單裡的技能才能寫進 §3 的「已安裝」區。**

### 5. 對沒有對應技能的分類，去 skills.sh 搜一輪

本機沒有，不代表生態系沒有。剩下的缺口逐一搜：

```bash
npx skills find "<分類的英文領域關鍵字>" < /dev/null
```

回傳 skills.sh 的結果、安裝數與 URL，可非互動執行。**搜到的東西一律只進「建議安裝」區，
不得當成可用技能**——它還沒裝，代理人呼叫會直接失敗。

搜尋結果必須過濾。實測搜「active directory」，前五名有四個是紅隊攻擊技能
（kerberos attacks、ACL abuse），把這種東西建議進唯讀健檢是事故等級的錯誤。
過濾規則、關鍵字怎麼下、建議欄怎麼寫，見 `references/skill-mapping.md` 的「到 skills.sh 找缺口」。

搜完仍然沒有合適的，就維持誠實寫法：在 §3 明說「無對應技能，改用 X 原生工具」。
為了把欄位填滿而推一個沾邊的技能，比空著危險。

### 6. 寫出 AGENTS.md

用 `assets/AGENTS.template.md` 當骨架，逐節填寫。各節的撰寫要點、好壞對照範例在
`references/agents-md-sections.md`，寫每一節前先讀對應段落。

欄位到節次的對照關係是這份技能的核心：

| 估算表欄位 | 餵給 AGENTS.md 的哪一節 |
|---|---|
| 項目分類 | §1 作業項目（每個分類一條 bullet）、§3 技能對應、§5 架構分層、§11 檢查項目 |
| 作業項目 | §1 每條 bullet 的內容（同分類的項目濃縮成一句，保留原文用詞） |
| 項次 | §4 提示檔的「涵蓋項次」欄、`progress.md` 的對照鍵——有它才驗得出覆蓋率 |
| 項目備註 | §6 技術堆疊（備註裡的 `Azure Portal → Subscriptions`、`Get-MgSubscribedSku` 就是工具清單）、§1 的括號補述 |
| 驗收項目 | §4 提示檔的驗收標準、§8 文件驗證、§11 交付前 checklist |
| L1/L2 工時 | 不寫進 AGENTS.md（工時是報價資訊，不是代理人的執行邊界），但可用來判斷該分類的份量 |
| 前置作業類分類 | §10 最小權限原則的依據（表上要什麼權限就只要什麼） |

生成 §4 提示檔時，若某個項次該歸哪一份提示檔、或驗收標準寫得不夠具體到能當
「完成」判準，不要自己腦補一個聽起來合理的版本——照 `references/clarifying-questions.md`
的追問協議問一輪，寫錯提示檔會讓代理人在錯的範圍裡驗收。

### 7. 展開 progress.md（計畫表）

AGENTS.md 定義的是「能做什麼」，但代理人還需要知道「還剩什麼沒做」。
把估算表整張展開成進度表，這件事才有答案：

```bash
python <skill>/scripts/init_progress.py <估算表路徑> --out progress.md
```

一個作業項目一列，狀態預設「未開始」，檔頭帶覆蓋率統計。
這份檔案同時是計畫表與進度表——邊做邊長的進度檔只回答得了「做過什麼」，
回答不了「還剩多少沒做」，而後者才是專案中期真正會被問到的問題。

重跑是安全的：腳本以作業項目為鍵**保留既有狀態**，只補新增項目；
估算表改版後被刪掉的項目會移到檔尾「估算表已無此項」等人工確認，不會靜靜消失。
所以估算表變更時直接重跑，不要手工同步。

### 8. 交付前自我檢查

- [ ] §1 的每一條都能指回估算表的項次；沒有任何一條是表上沒有的
- [ ] 估算表的每個分類都在 §1 出現，沒有整段漏掉（含「其他」類的 PM、應變工時）
- [ ] §3「已安裝」區的技能都真實存在且已安裝；沒有對應的分類有誠實說明
- [ ] §3「建議安裝」區與「已安裝」區分開，沒有把還沒裝的技能寫成可用；每一條都附安裝指令、安裝數與本案的使用限制
- [ ] §5 的分層與 §1 的分類對得起來，沒有憑空多出來的系統
- [ ] §6 的工具都能在備註欄找到出處
- [ ] §10 的安全基調符合步驟 2 判斷的作業性質
- [ ] §11 的檢查是這個專案真的能執行的動作（沒有 CI 的專案不要寫「跑 npm test」）
- [ ] `progress.md` 已展開，列數與估算表的作業項目數一致
- [ ] §2／§4 保留「一次只處理一個項次、提示檔即將動手才生成」的限制，沒有在客製時被精簡掉
- [ ] 全篇沒有夾帶估算表裡的帳密、對外 IP、客戶內部網段
- [ ] 過程中曾經升級成決策題的追問都已經拿到使用者回答，沒有邊寫邊用猜的補完

最後把估算表的路徑寫進 AGENTS.md（範本 §1 開頭那句「依 `<估算表檔名>` 整理」），
之後有人要驗證範圍時才找得到來源。

## 常見誤區

**把估算表當靈感而非邊界。** 看到「AD 健檢」就自動補上一堆最佳實務項目——那些沒報價。
估算表寫了 18 條就是 18 條。

**技能清單抄範本。** 別的專案的 AGENTS.md 列了哪些技能跟這個專案無關，
一定要按步驟 4 實際盤點。

**驗收欄漏讀。** 驗收項目常常是合併儲存格或打錯欄，最容易整段掉。§8、§11 沒有內容通常就是這裡漏了。

**把工時寫進去。** 代理人不需要知道這件事估 240 分鐘，寫進去只會讓它自我設限或洩漏報價資訊。

**§4 提示檔一次生成一批。** `progress.md` 把估算表全部展開成「未開始」是為了看得到全貌，
不代表代理人該順手把每個項次的提示都一次寫完。提示檔要在**即將動手做那一項**時才生成、
一次一份，做完才回頭挑下一項——見範本 §2 步驟 2／7／12 與 §4 開頭。
一次生成一批，會讓使用者只能整批核准，逐項把關的設計就失效了。
