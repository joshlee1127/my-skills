# 各節撰寫指引

寫每一節之前先讀這裡對應的段落。範例取自一份 IT 環境健檢的工時估算表（分類為
「1. Azure 前置作業」「2-A.Azure 資安項目檢查」…「9.報告產出」「其他」）。

---

## §1 產品——最重要的一節

這一節是代理人的範圍邊界，其他節都從它衍生。

**一個項目分類 = 一條 bullet。** 分類名稱做粗體開頭，冒號後把該分類底下的作業項目
用頓號串成一句。保留估算表的原始用詞，因為客戶會拿這份文件對範圍。

估算表：

```
1. Azure 前置作業 | 1.1 健檢標的訂閱清單確認
                  | 1.2 提供 Entra Global Reader 權限   （備註：建議使用 Global Reader 或 Security Reader 避免過高權限）
                  | 1.3 提供 Log Analytics 存取權限
                  | 1.5 啟用Azure Monitor
                  | 1.6 啟用VM Insights
```

✅ 好：

```markdown
- **Azure 前置作業**：健檢標的訂閱清單確認、Entra／Log Analytics／Backup Center 權限取得、
  啟用 Azure Monitor／VM Insights／Azure Advisor
```

❌ 壞（自行擴充了表上沒有的項目）：

```markdown
- **Azure 前置作業**：訂閱清單確認、權限取得、啟用監控工具、**建立資源標籤規範**、
  **設定成本預算告警**
```

後兩項沒有報價，代理人會照做，然後你多花了工時。

❌ 也壞（濃縮到失去可驗證性）：

```markdown
- **Azure**：做 Azure 相關的健檢
```

驗收時無法對照項次。

**「其他」類不要漏。** PM 支援、應變工時、內部討論、文件整合這些也是報價項目，
漏掉會讓代理人以為這些事不該做。

**結尾固定收一句**「不要過度建構，也不要新增未在估算表中列出的作業項目」。
這句話是整份文件的錨點，刪不得。

---

## §2 工作流程

多數專案沿用範本的十步流程即可。要調整的是措辭：唯讀健檢寫「盤點需求」，
建置專案寫「實作需求」。

若估算表明確有「前置作業」分類（要客戶提供權限、帳號、圖資），在流程開頭加一句
「確認前置作業所需資料已齊備」，因為缺料就開工是這類專案最常見的返工原因。

---

## §3 技能

見 `skill-mapping.md`。原則一句話：**已安裝的才算可用，沒安裝的只能是建議，兩者不可混在同一區。**

三個區塊各有各的責任：「已安裝並核可使用」是代理人現在就能呼叫的；「建議安裝」來自
`npx skills find` 且已過濾，需使用者核准才會存在；「沒有對應技能的分類」寫替代手段。
沒有內容的區塊整段刪掉，不要留空表格。

---

## §4 提示檔案

固定結構（涵蓋項次／目標／已閱讀技能／已檢視資料／決策假設／會變動的檔案／實作需求／
安全需求／驗收標準／要執行的檢查／手動測試步驟）。

要客製的有兩項：

**涵蓋項次**——這份提示對應估算表的哪幾條（例：`2.1–2.9`）。加這一欄的理由是覆蓋率：
沒有它，就沒辦法回答「`prompts/` 底下的檔案全做完，是不是等於整張表做完」。
有它，才能拿 `progress.md` 逐條對帳。

**驗收標準**——直接引估算表「驗收項目」欄的內容。
例如報告產出的驗收欄寫了「架構圖／主要資源清單／系統角色分類」，
那份提示的驗收標準就該長這樣，而不是泛泛的「報告完整」。

檔名建議用分類的英文短名（`prompts/azure.md`、`prompts/network.md`），
一個分類一個檔，方便對照 §1。

工時大的分類要切多份。判斷依據是估算表的工時欄——720 分鐘、18 個項目的 AD 健檢
塞不進一份提示，切成複寫／DNS／帳戶盤點／GPO 幾份較實際。
工時本身不寫進 AGENTS.md，但它是切分批次的線索。

## §5 架構

**分層直接對應項目分類，不要憑空補系統。**

分類「4.伺服器盤點」的作業項目提到 VMware ESXi、vCenter、作業系統版本，
那這一層就寫這些；表裡從沒出現 Kubernetes，就不要因為「現代架構通常有」而寫進去。

每層的組成元件從作業項目與備註欄撈。例如網路健檢的備註寫了
「查看機房外網數據機…（主要是台北辦公室及台南辦公室，菲律賓遠端支援）」，
架構層就該寫出這三個據點。

收尾補一條跨層限制。健檢型專案常見的是：報告產出層只能呈現既有結果，
不得反過來觸發作業或變更狀態——這防的是代理人為了補一張圖而去重跑一次掃描。

## §6 技術堆疊

**主要來源是「項目備註」欄。** 備註欄裡的工具名稱、管理介面路徑、PowerShell 指令，
逐一收斂成工具清單，每一項標註它服務的作業項目。

備註：`Entra Admin Center → Roles`、`Azure Resource Graph`、`Get-MgSubscribedSku`

```markdown
- Entra ID（Azure AD）Admin Center——Global Admin／角色、Conditional Access、MFA 狀態檢查
- Azure Resource Graph——訂閱、資源、Public IP 盤點
- Microsoft Graph PowerShell——M365 帳號與授權盤點
```

「不要使用」清單同樣要有依據：從作業性質推（唯讀專案 → 禁止變更類指令）、
從授權範圍推（禁止未授權的第三方掃描工具）、從資料落地推（禁止約定以外的儲存位置）。
不要寫一串與本案無關的通用禁令。

## §7 文件

`doc/` 放交付文件、`data/` 放原始輸出且不進版控，這兩條幾乎所有專案通用。

要客製的是：

- **機敏資料的具體類型**——從估算表推。有 AD 盤點就會有帳號清單與群組成員，
  有網路健檢就會有設備 Config 與防火牆 Policy。寫具體的，代理人才知道要警覺什麼。
- **外部同步**——如果專案有同步到 SharePoint／雲端硬碟的需求，務必寫清楚三件事：
  同步時機在機敏資訊清理之後、方向是單向、以及禁用會刪除目的端既有檔案的參數
  （例如 `robocopy /MIR`）。順序反了，未清理的資料就已經出去了。

---

## §8 文件驗證與清理

四段固定：內容正確性、機敏資訊清理、格式與結構、清理。

**內容正確性**的核心句是「可回溯至實際執行的作業，不得憑空捏造或臆測」。
健檢報告最大的職業風險就是代理人把「合理推測」寫成「盤點結果」。

**機敏資訊清理**要點名高風險來源——從估算表看哪些作業會產出憑證類資料：
設備 Config 匯出、防火牆 Policy、PowerShell 執行紀錄貼附內容。

三條通用規則，照抄即可。有特殊憑證管理需求（例如客戶用 PAM 工具）再補。

## §10 安全性與最終規則

**基調由作業性質決定**，這是全篇最不能寫錯的地方：

| 作業性質 | 核心句 |
|---|---|
| 唯讀健檢 | 一切作業以唯讀盤點為前提，絕不執行會變更正式環境設定或狀態的操作 |
| 變更型導入 | 任何變更需事前核准、變更視窗、回復計畫與變更前備份 |
| 混合 | 逐條列出哪些項次唯讀、哪些允許變更，不要留模糊地帶 |

**最小權限**要引估算表前置作業欄的具體角色。表上寫「提供 Entra Global Reader 權限」，
就寫「優先使用 Global Reader、Security Reader、vCenter Read-Only，不得擴大範圍索取」——
比抽象的「遵循最小權限原則」有用得多，因為代理人真的會照著要權限。

**最終規則**是一份八步 checklist，作用是當代理人卡住時有個回歸點。保持它短。

## §11 指令與檢查

**誠實寫這個專案真的能跑什麼。** 大多數健檢／盤點專案沒有 build 或 CI，
那就明說「本專案沒有建置或 CI/CD 流程，『執行可用的檢查』指的是以下人工／半自動檢查」。
寫一個跑不了的 `npm test` 只會讓代理人假裝跑過。

常見且有價值的檢查：

- **腳本唯讀性檢查**（唯讀型專案必備）：逐行確認只含唯讀動詞（`Get-`、`Show`、`Test-`、`dcdiag`），
  不含 `Set-`、`Remove-`、`New-`、`Restart-`、`Disable-`。
- **機敏資訊關鍵字掃描**：grep `password`、`secret`、`key`、`token`。
- **文件連結與圖片路徑檢查**。
- **交付前 checklist**：指回 §8。

工具（`PSScriptAnalyzer`、`markdownlint`）寫成「若環境有安裝可執行，作為輔助而非強制門檻」，
避免代理人因為缺工具而卡住。

結尾這句要留：「回報時，明確說明實際執行了哪些檢查與結果；未執行過的檢查，不要宣稱已經通過。」

## §12 進度與紀錄

關鍵設計：**`progress.md` 由估算表整張展開，不是邊做邊長。**

差別在於它能回答什麼問題。邊做邊長的進度檔只記錄發生過的事，
回答得了「做過什麼」，回答不了「還剩多少沒做」——而專案中期客戶問的永遠是後者。
一開始就把 94 個作業項目全部展開成「未開始」，覆蓋率才算得出來。

用 `scripts/init_progress.py` 生成，不要手工建：

```bash
python <skill>/scripts/init_progress.py <估算表路徑> --out progress.md
```

欄位：項次／作業項目／狀態／更新日期／備註，依估算表的分類分節，檔頭一行覆蓋率統計。

§12 要寫進 AGENTS.md 的三條規則：

- **不得新增估算表上沒有的列**——那等於在進度表上偷渡範圍外的工作，
  是 §1 那條「不要新增未列出的作業項目」在進度層面的對應。
- **不適用的項目改狀態，不刪列**——刪掉覆蓋率就對不上估算表了。
- **估算表改版時重跑腳本，不要手工同步**——腳本會保留既有狀態，
  並把估算表已刪除的項目移到檔尾等人工確認。手工同步遲早會漏。
