# 2. 工作流程

針對每一個{{實作／盤點}}需求：

1. 閱讀 `AGENTS.md`。
2. 讀 `progress.md`，只挑**一個**要做的項次，確認它的前置作業是否已完成。
   {{前置作業類分類}}沒完成就往下做，會做到一半卡在缺權限或缺資料——寧可先回頭要料。
3. 閱讀使用者明確提到的技能（skills）。
4. 從核准的技能清單中，閱讀明顯需要的支援技能。
5. 檢視相關{{程式碼／既有資料}}。
6. 只有在任務有明顯歧義時，才提出一個聚焦的問題。
7. 只針對這一個項次，在 `prompts/` 中建立一個詳細的提示檔案，並在 `progress.md` 把對應項次改為「進行中」。
8. 詢問：「我已在 prompts/`<file-name>`.md 準備好提示。可以執行了嗎？」
9. 獲得核准後，重新閱讀該提示檔案，並嚴格依此執行。
10. 執行可用的檢查（見 §11）。
11. 更新 `progress.md` 對應項次為「已完成」，並分享測試或驗證的確切步驟。
12. 回到步驟 2，挑下一個項次——不要提前跳過去。

除非使用者明確表示要跳過提示建立步驟，否則不要在建立提示之前就開始動手。

**一次只處理一個項次。** `progress.md` 一開始就把所有作業項目展開成「未開始」，
是為了看得到全貌與剩餘工作，不是要一次把每個項次的提示都寫完。
不得預先幫還沒要動手的項次批次建立提示檔——每份提示都要對著使用者當下核准的那一項，
批次生成等於讓核准機制形同虛設。

# 4. 提示檔案（Prompt files）

提示檔案存放在 `prompts/`，依{{分類}}命名，例如 `prompts/{{範例}}.md`。

**一次只生成一份，且只在即將動手做那個項次時才生成**（見 §2 步驟 7）。
不得在展開或讀取 `progress.md` 時，就把裡面所有「未開始」的項次一次性寫成整批提示檔——
那會讓使用者只能對著一整批提示按核准，而不是逐項把關。

每個提示檔案都必須包含：

- **涵蓋項次**——這份提示對應{{估算表}}的哪幾條項次（例：2.1–2.9）。
  沒有這欄就無法驗證「所有提示做完 = 整張表做完」，覆蓋率會變成一筆糊塗帳。
- 目標
- 已閱讀的技能
- 已檢視的既有{{程式碼／資料}}
- 決策或假設
- 可能會變動的檔案
- 實作需求
- 安全性需求
- 驗收標準　<!-- 直接取自估算表「驗收項目」欄 -->
- 要執行的檢查
- 完成後預期的確切手動測試步驟

# 12. 進度與紀錄

所有作業進度統一記錄在專案根目錄的 `progress.md`，不得散落在其他檔案或僅存在對話紀錄中。

**`progress.md` 同時是計畫表與進度表**：它由{{估算表}}整張展開而來，所有作業項目一開始就在裡面，
狀態預設「未開始」。這是刻意的設計——邊做邊長的進度檔只回答得了「做過什麼」，
回答不了「還剩多少沒做」，而後者才是專案中期會被問到的問題。

## 動作前檢查

- 開始任何動作前，先讀取 `progress.md`，確認要做的項次、其前置作業是否完成、以及整體剩餘工作。
- 不要在 `progress.md` 新增{{估算表}}上沒有的列——那等於在進度表上偷渡範圍外的工作。
- 若 `progress.md` 尚不存在或與{{估算表}}不同步，用 `{{init_progress 腳本路徑}}` 重新展開；
  重跑會保留既有狀態，不要手工同步。

## 更新時機

- 每個動作開始前：把對應項次的狀態改為「進行中」。
- 每個動作完成後：改為「已完成」，補上更新日期與結果摘要（不得寫入機敏資料）。
- 動作中止或延後時：改為「延後」並註明原因。
- 經確認不適用的項目：改為「不適用」並註明理由——直接刪列會讓覆蓋率對不上{{估算表}}。

## 格式

以表格記錄，依{{估算表}}的項目分類分節，每列包含：項次、作業項目、狀態
（未開始／進行中／已完成／延後／不適用）、更新日期、備註。
檔頭維持一行覆蓋率統計（已完成 / 總項目數）。

## 分離原則

`progress.md` 只記錄進度與狀態，不得包含帳密、金鑰、Token；機敏資訊處理依 §9、§10。
